# 工作流

## 一次改动的顺序

1. **读**：根 `AGENTS.md` → 相关目录 `AGENTS.md` → `docs/agents/STATUS.md` → 对应设计 spec / 裁定。
2. **查**：先 `deja_recall` / `grep` 找既有实现与历史决定，不重复造；继承来源只读对照。
3. **判**：设计改动写 spec；维护改动写 `MAINTENANCE_RULINGS.md`；两者都不沾才直接改代码。
4. **改**：单仓内改，一次只做一个可独立验证的责任区；不跨项目 `git add -A`。
5. **验**：按 `VERIFICATION.md` 跑，留下命令、rc、测试数与证据路径；没跑写 `NOT_RUN`。
6. **记**：更新 `STATUS.md`（改动、命令、rc、证据、未验证）。

## 调查先行的硬规则（M-001）

- 用户说「先调查」「不要急着写代码」时**不写代码**：只做只读取证、可行性判断、落点定位。
- 调查产出写 `docs/superpowers/reports/`，结论回写到 `STATUS.md`。
- 汇报后再动手；汇报里必须列「需要用户拍板的岔路」，不替用户做设计决定。
- 继承来源目录只读：不改、不提交、不清理、不重启其仓库或运行实例。

## 需求落地的硬规则

- 没有 spec 不进入实现；spec 至少包含：需求原话、范围/非目标、不变量、验收判据、未决问题。
- 技术选型、模块划分、数据模型、运行时宿主形态属于设计裁定，必须由用户确认或明确授权。
- 不在初始化期「顺手」创建 Maven/Gradle/npm 工程；构建文件本身也是设计决定。

## 跨项目改动的顺序

本项目当前只有一个仓库。若未来需要对照或吸收继承来源：

1. 先在 `docs/upstream/` 记录来源路径、commit、日期与契约摘要；
2. 再在本仓写 spec，说明吸收什么、丢弃什么、如何验收；
3. 最后才复制/改写代码，并保留来源与许可证信息。

继承来源的内部顺序（`iiBotMosire` → `InboxMosire` → 宿主适配器）只作为调查事实，不是本项目的构建顺序。
