# 普通优先级 Inbox 长间隔

> 状态：已确认，2026-11-21（UTC+8）。

## 需求

> 第二个问题是bot自己维护的，你不用管，你只需要出0.0.8-hotfix1来修复低权限消息的注入间隔无法设置很大就行，最高允许设置到24h

普通档是低于 `weighting.immediateThreshold` 的条目。修复沿用现有 Inbox 调度和 `set_config`，发布为 `0.0.8-hotfix1`。

## 不变量

1. `weighting.normalDelaySeconds` 可热改，接受 `0..86400` 秒。出厂值仍沿用已确认的 60 秒。高优先级延迟保留其原有范围。
2. 开启首次推送硬上限时，普通档取配置的首次推送上限与普通延迟两者的较大值。以条目创建时间为锚，持续活跃和进程重启都不重新计算首次推送起点。高优先级照常使用现有首次推送上限。
3. 来源安静窗口可以延后普通档的独立唤醒，来源最大等待只限制安静窗口的附加等待。其他到期条目触发的同批推送继续沿用现有窗口与安静判断。
4. 通过入站过滤的消息照常写入原始消息板。骰娘控制、ACK 与其他产品行为沿用现有契约。

## 验收判据

- `set_config` 可写入 1800 和 86400，拒绝 86401 并保留上一份有效配置。
- 使用默认 60 秒首次上限和启用的来源安静规则，普通条目的 `nextPushAt` 仍显示 1800 秒或 86400 秒后的期限。持续合并同源消息或重启后，保留首条创建时间。以时间戳与到期条目验证，避免真实等待。
- 独立高优先级条目照常使用短延迟；高优先级唤醒可携带符合现有条件的普通条目。
- 版本与可下载资产一致，通过回归、Linux 打包烟测及校验和复核。
