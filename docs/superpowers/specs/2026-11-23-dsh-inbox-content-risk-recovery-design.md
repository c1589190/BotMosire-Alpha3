# DSH Inbox 内容审核失败恢复

> 状态：已确认 · 2026-11-23（UTC+8）

## 需求与范围

> 那有没有重试机制，就是dsh插件主动检测是否出现相关问题，如果有，取消本次注入、删除相关上下文元素之类的，是否可行？

> 那么开始修改？

自动恢复属于 DSH Inbox 投递，挂在 Inbox 模块。现有 BMA3 角色预设、DeepSeek 审核、常规 DSH 重试以及 D-082 的会话压缩契约继续适用。

## 目标行为

Inbox 在 DSH 的 `agent/request-error` 钩子检查当前绑定会话的第一步。仅处理 `deepseek-official` 的 HTTP 400、`INVALID_REQUEST` 且消息为 `Content Exists Risk` 的失败。该步须存在一条刚由 BMA3 唤醒的面板，具有可核对的消息 ID、revision 和 pushRevision。用户自己的输入、稍后的工具续步、未知归属和旧历史不触发恢复。

通过 DSH 追加一条单节点 `replace`，用固定的无正文通知替换该面板在后续请求中的位置，保留原批次标识。替换实际生效后由 DSH 在同一步重新组装请求并重试一次。原始会话事件和消息板原始记录分别保存在会话日志和消息板，替换只改变模型可见的会话历史。服务端仍可能因同一请求中的其他内容而拒绝。

替换后同一步再次收到同种拒绝时，沿用现有 Inbox 暂停语义停止后续自动唤醒，记录不含正文的暂停诊断。下次手动操作可用现有 `/inbox status`、`/inbox resume`。宿主缺少写入或重试能力时，此恢复路径不介入。

## 不变量

- 仅替换当前绑定、当前第一步内仍对模型可见的 BMA3 面板，保留其他会话输入。替换事件必须引用被替换的事件。可从当步事件识别已做出的替换，避免重入再试。
- 只有模型可见历史发生对应变更才请求重试。第二次审核拒绝结束本步。暂停持久化故障须可观测，当前进程保持暂停。
- Inbox ACK 仍确认原面板的已投递事实，使用原服务端身份、revision 和 item IDs。该恢复不再次调用 `followup`，不触发 QQ 发送，不回滚 ACK 或重推已冻结条目。
- 诊断仅使用错误码、批次 revision 和 pushRevision。无自动历史扫描或清理旧失败会话。

## 验收判据

- 从已注入的新面板触发首个匹配拒绝。只替换该条，原文从下一次模型请求移除，原始日志与其他输入保留，同一步仅重试一次。
- 替换后再次拒绝，自动注入进入暂停。重入不会产生第二次替换，ACK 不回退。确认暂停能跨插件重启恢复，保存失败时当前进程仍暂停。
- 普通 400、413、其他 provider、人工提示、别的会话、其他步骤、已被压缩/替换的节点、取消与宿主能力缺失均保留 DSH 原流程。
